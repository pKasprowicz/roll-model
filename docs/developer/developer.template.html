1. Introduction

Roll Model is a desktop application for drummers, written in Rust with the egui immediate-mode GUI. It loads MusicXML drum scores (or generates one of the 40 PAS drum rudiments), plays them, captures a Roland V31 drum module over MIDI, draws the played notes under the written ones and grades the performance. A control surface (Mackie Control or plain MIDI) can drive it, and you can teach the program a new one by pressing its controls.

This guide is for someone who wants to change the program: fix a bug, add a feature, port it, or learn how a real-time desktop application can be structured in Rust. It explains the ideas first, then the code, then walks through concrete changes step by step.

2. Getting started

Build, run, test

You need a recent Rust toolchain (rustup; 1.99 is the tested version, 1.85 the oldest that can parse the dependencies). On Linux install libasound2-dev and pkg-config first.

cargo run --release                                  # start empty
cargo run --release -- examples/basic_rock_beat.musicxml
cargo test                                           # every test of both crates (no devices needed)
cargo test -p roll-model-core                        # the core alone: builds no GUI, MIDI or audio crate
cargo doc -p roll-model-core --no-deps --open        # rustdoc of the core
cargo build --release --no-default-features          # without the sound card (no cpal)
cargo check --no-default-features                    # quick check of the other feature set
  • It is a Cargo workspace of two crates: roll-model (the application: window, MIDI ports, sound; src/) and roll-model-core (everything that needs none of them; core/). default-members makes cargo build and cargo test cover both. A single test runs with cargo test the_hands_are (a test of the application is in the binary's test target, a test of the core in the library's). The application re-exports the core's modules at its root (use roll_model_core::{analysis, config, …} in main.rs), so its code writes crate::analysis.
  • Use a release build for anything that depends on timing (recording takes, keyboard pads): debug frames are slow enough to make timestamps unreliable.
  • The feature audio (default) pulls in cpal. Without it the click and Listen can still go to a MIDI output. Code that needs the sound card is behind #[cfg(feature = "audio")] with a stub for the other case.

Building the documentation

python3 tools/build_manual.py       # target/manual/roll-model-manual.html
python3 tools/build_devguide.py     # target/devguide/roll-model-developer-guide.html (this file)
python3 tools/build_notices.py      # target/notices/THIRD_PARTY_NOTICES.txt

All three use only the Python standard library. They run in CI during a release.

Workflow and conventions

  • Branches. main holds releases, develop the work in progress, feature/<name> branches are merged into develop with a merge commit. Moving the tag preview onto a commit of develop and pushing it builds a pre-release.
  • Versioning is SemVer. The version lives in Cargo.toml and core/Cargo.toml (bump Cargo.lock with them), release tags are vX.Y.Z. Every user-visible change goes under [Unreleased] in CHANGELOG.md.
  • Commit messages are feat:, fix:, docs:, chore:, test:, ci: followed by a sentence.
  • Keep the core crate pure. The crate core/ (roll-model-core) holds analysis.rs, musicxml.rs, notation.rs, score.rs, drums.rs, xml.rs, rudiments.rs, trigger.rs, controller/ and controller_layout.rs, loader.rs and config.rs. It cannot depend on the app crate, and its manifest lists no GUI, MIDI or audio crate, so the compiler enforces what used to be a convention. That is what makes it testable without devices (cargo test -p roll-model-core, with integration tests in core/tests/).
  • Time is quarter notes. Score positions are quarter notes (q); convert to seconds only through TempoMap.
  • Style. Write code that reads like the code around it: same comment density, naming, idiom. Doc comments say why and what the caller can rely on; a test name is a sentence describing behaviour.
  • Update the docs with the code. HANDOFF.md (status, architecture list, conventions), the README, the manual template and, if behaviour is user visible, the changelog. This guide's code excerpts update themselves; its prose does not.
  • Glyphs. egui 0.29's default fonts lack several symbols (a filled circle, a cross, an arrow); a missing glyph is drawn as a box. Check any new glyph in the running app before using it. The proven ones are listed in HANDOFF.md.

Debugging and looking at the UI

  • No kit? Tick Settings → General → Computer keyboard plays pads. The keys call the same handle_event as a real MIDI hit (time-stamped at frame time).
  • Monitors. Settings → MIDI input shows every drum hit; Settings → Controller shows every controller message and what it is bound to.
  • Seeing a screen without clicking. There is no UI test harness, so to look at a tab temporarily set app.tab (and any state) at the end of DrumApp::new, build, start the program with APPDATA pointing at a scratch folder (so your settings are not touched) and screenshot its window. Remove the patch afterwards. Headless egui::Context::run tests cover that a screen draws without panicking.
  • A scratch settings folder. The settings and the controller presets live in %APPDATA%\RollModel (and equivalents). To try a preset or a setup without touching yours, start the program with APPDATA pointing at a scratch folder that holds a config.txt and a controllers folder. The tests never touch the real folder: DrumApp holds a Paths (config::Paths: the settings, sounds and controllers folders). The program has Paths::system(); a DrumApp made for a test has Paths::none() (nothing is read, saving fails), or Paths::in_dir(temporary folder) when the test needs files.
  • Several windows. The splash and the Manage window are windows of their own, so a screenshot must pick the right one: capture each OS window by its title (on Windows PrintWindow on its handle), and give a click or key a moment to arrive (the program handles input once per frame).
  • Logging. There is no logging framework; use dbg!/eprintln! from a debug build (the Windows release build hides the console).
  • Sound. Nothing in the test suite hears anything. On Windows the per-application peak meter of the output device is the way to see that the program is silent or sounding (see HANDOFF.md → Testing).

3. Architecture

Layers

The program has three layers. Dependencies point downwards only: the UI knows the devices and the core; the devices know the core; the core knows nothing about either. The lowest layer is a crate of its own, core/, whose manifest lists only zip: it cannot use the window, MIDI or audio crates, so the rule is enforced by the compiler instead of by review.

The payoff is visible in the tests: matching and grading, the rudiment builder, the MusicXML importer, the controller mapping and the playback scheduler are all tested with no MIDI port, sound card or window.

Data flow

Besides the queues, two paths are worth knowing. Start-up is not a data path but a sequence: the program builds itself in small steps over the first frames, one device at a time, so the window can show what it is doing (Start-up). Editing a controller preset writes a text file and swaps the running mapper's preset; nothing is reconnected (Editing presets).

Three rules keep this simple. Callback threads only append to a Mutex<Vec> (MIDI) or read a wait-free queue (audio); they never touch application state. The sound threads never block on the UI: they read atomics and plain data they were given at start. The audio callback never locks, allocates or frees, because it has about ten milliseconds to fill a buffer and a late buffer is a click you can hear. The UI thread alone owns DrumApp.

The next chapters follow the same data: chapter 5 lists every thread and what it owns, and chapter 6 follows one sound from the moment the score says "now" to the moment the sound card plays it, including where the delay comes from.

4. Core concepts

Time

There are two kinds of time and they must not be mixed.

  • Score time is in quarter notes from the start of the (unrolled) score: q. A bar of 4/4 is 4.0 long, a 16th note is 0.25, a triplet 16th is 1/6.
  • Wall time is in seconds. It exists only through TempoMap, a piecewise-constant tempo curve, with a scale factor for the practice tempo.
{{code:core/src/score.rs::pub struct TempoMap}}

q_to_sec(q, scale) and its inverse sec_to_q are the only conversions; sec_to_q extrapolates for negative times, which is how a count-in lands before the first bar. Rudiment scores are written at a fixed 100 BPM and use the scale as the BPM (see The rudiment subsystem).

Take time zero is the start of the first measure of the practice range. Take.t0 is that measure's absolute time, so a hit's score position is sec_to_q(hit.t + t0, scale). In start_take zero is now + 0.5 s lead + count-in: half a second is reserved so the sound device has time to open, so the first score note comes 0.5 s after the count-in alone would suggest. Anything that scripts a take from outside has to add that lead.

The score model

A Score is deliberately flat: a time-ordered list of drum onsets, a list of measures and a tempo map. Nothing in it knows where it came from. A MusicXML file, a rudiment and the metronome's click bar all produce the same type, which is why Listen, takes, grading and the staff work on all of them.

{{code:core/src/score.rs::pub struct ScoreNote}} {{code:core/src/score.rs::pub struct Score}}
  • staff_step: step 0 is the bottom staff line (E4), the top line (F5) is step 8; each step is one line or space. Played notes are drawn where the score draws the same lane (Score::staff_for_lane).
  • grace / grace_order: a flam is one grace note, a drag two; order 1 is nearest the main note. They have the same q as the main note and are placed in front of it in notes.
  • hand: only rudiments set it. It drives the sticking letters and the per-hand statistics.
  • Repeats and voltas are unrolled by the importer, so score time is always the order of playing.

The kit: lanes and note maps

A Lane is an instrument as the program sees it (kick, snare, cross-stick, closed/open/pedal hi-hat, four toms, two crashes, ride, bell, china, splash, cowbell, other). Everything that varies per instrument is a match on Lane, so adding one is a compiler-guided change (tutorial 6).

{{code:core/src/drums.rs::pub fn family::12}}

A NoteMap maps MIDI notes to lanes; NoteMap::roland_v31() is the factory map and the user can edit it. Lane::by_hihat_pedal turns a hit on the closed or open hi-hat note into one or the other from the pedal position (CC#4) attached to the hit.

The life of a take

  1. plan_run works out the range, tempo scale, count-in, time zero and the click track for the practice range. Takes and Listen share it, so what you hear is what a take asks for.
  2. start_take expands the score into Expected notes (seconds, relative to the start of the range), starts a Metronome thread for the count-in and click, and stores a Take with an empty report.
  3. drain_midi and handle_event (every frame) turn queued RawEvents into Hits. handle_event is a sequence of named steps, each of which sees every event: learn_note (MIDI-learn of a pad), the monitor, record_calibration_hit, then the start trigger (the one step that can consume the event) and record_take_hit, which maps the note to a lane, applies the hi-hat pedal, subtracts the latency and keeps hits from three quarters of a count-in beat before zero on.
  4. update_take re-analyses the whole take every frame (it is cheap) so the colours appear as you play; notes later than the elapsed time stay Pending.
  5. stop_take freezes the report, pushes a TakeSummary to the history and, for a clean rudiment take, records the best tempo.

Matching and grading

analysis.rs is a pure function from (expected, hits, tolerances, elapsed) to a Report.

  1. Candidates. Every (expected, hit) pair within the hit window of the expected note is a candidate: same lane at cost |dt|, a related lane (same family: snare/cross-stick, closed/open hi-hat, ride/bell, the crashes) at cost |dt| + 40 ms and flagged wrong pad.
  2. Assignment. Pairs are taken cheapest first, one-to-one (greedy). That is simple, deterministic and good enough for drum scores; an optimal assignment would only matter for pathological overlaps.
  3. Grades. Perfect, good, OK by |dt|, wrong pad, missed; notes later than the elapsed time are pending and excluded from the statistics. Grace notes are optional: never missed, and a hit that matches one is not extra.
  4. Summary. Accuracy (credit-weighted), mean/abs/std of offsets, drift (regression slope of offset over time), timing score, extra hits, dynamics (accents louder than the median plain stroke, ghost notes softer), per-lane and per-hand statistics, and feedback sentences.
  5. Overall = 55 % accuracy + 25 % timing + 10 % (1 − extra ratio) + 10 % dynamics; without accents/ghosts the dynamics weight is redistributed. The weights are first guesses.

MIDI input

midir calls a closure on its own thread for every message. The closure takes Instant::now() first, remembers the last hi-hat pedal value, and for a note-on pushes a RawEvent into Arc<Mutex<Vec<RawEvent>>>. The UI thread std::mem::takes the vector once per frame.

The queue lock is the only synchronisation. Timestamps are made before the lock, so a busy UI thread delays only the processing of a hit, never its time.

The timing threads

Two kinds of thread schedule sounds: Metronome (the count-in and click of a take, and the calibration clicks) and Player (Listen, the free metronome, the audition button). Both walk a sorted list of (time, what) and wait for each target with the same helper: sleep coarsely, then spin for the last 1.5 ms.

A Player owns one MIDI connection so that the click and the drums can share a MIDI port (Windows ports are exclusive); its sound goes to the audio engine (below). Cues that are more than 250 ms late are dropped rather than played as a burst. stop() sets an AtomicBool and joins the thread; Drop calls stop(), so letting a handle go out of scope cannot leak a thread.

The sound itself is made by the audio engine (src/audio/), which is the subject of chapter 6. What matters for the scheduler threads is this: they do not make sound, they tell the engine when each sound should start, as an Instant, about 30 ms ahead (AUDIO_LOOKAHEAD), and the engine starts it at the exact frame of its output stream. MIDI, which has no buffer to place a sound in, is held back to its exact time instead.

DrumApp.listen exists only while the playhead runs; the player may outlive it by up to 2.2 seconds so the last cymbal rings out.

Shared live settings

Click on/off, notes on/off, looping, volumes and per-instrument gain must change while sound plays. They live in Control, a struct of atomics shared by Arc. Floats are stored as their bit pattern in an AtomicU32, so the sound threads read them without locks.

Tempo ramp

A looping run can speed up: PlayOptions.ramp is a Ramp { every, step }. The cues of a pass are always given for the starting tempo; run_with squeezes pass p by 1 / factor(p) and starts it where the shorter earlier passes ended (start_of), so there is no gap and no new cue list. Everything that shows where the music is (Listen's playhead and label, the metronome's beat lights and rolling staff) asks Ramp::locate or base_seconds to turn real seconds into seconds at the starting tempo, and then works as before. The count-in is never squeezed. The test with the fake sink measures the gaps between cues.

6. The audio system

This chapter explains how a sound gets from the score to the speaker, why that takes time, which part of that time the program can influence, and how the engine in src/audio/ is arranged to remove the part that matters most. It is the longest chapter on purpose: the engine is small, but every piece of it exists because of a property of audio hardware that is easy to forget. The history and the measurements are in docs/audio-engine-plan.md; this chapter is the explanation. Words underlined with dots are explained in the glossary at the end of the chapter, at their first use.

The problem: constant delay is harmless, jitter is not

The program plays a click or a drum sound and judges the drummer's hits against the same clock. Two different things can go wrong with the sound:

  • A constant delay: every sound comes out, say, 30 ms after the program asked for it. The drummer plays to what they hear, so every hit arrives 30 ms after the program's idea of the beat. That is a fixed offset, and Calibrate measures it and subtracts it (latency_ms, applied in one place, record_take_hit). After calibration a constant delay costs nothing in grading.
  • Jitter: the delay is different for each sound. Calibration cannot remove it, because there is no single number to subtract. It also blurs the calibration itself, since the median of a wobbling delay is only a middle value.

The scale matters. A hit counts as perfect within 20 ms and good within 45 ms of its note, and a sixteenth note at 240 BPM is only 62.5 ms long. A jitter of 10 ms eats half of the perfect window before the drummer has done anything. So the aim of the engine is steady timing first, low delay second: the second is nice to have, the first is what makes grading fair.

There is also a second sound path that does not suffer from any of this: the click and the drums can be sent over MIDI to the drum module, which makes the sound itself. A MIDI note is a few bytes sent at an exact moment; the module's own latency is small and constant. The audio engine exists for the case where the sound has to come out of the computer.

Where the delay comes from

From "the score says now" to "the air moves" there are several stages. Some belong to the program, some to the operating system, some to the hardware. The figure follows one sound.

1 and 2. The scheduler. A thread (Player or Metronome) knows when a sound should start, as an Instant. An operating system does not wake a sleeping thread at an exact moment, so the helper wait_until sleeps in coarse steps and spins for the last 1.5 ms. Even so a wake-up can be a little late. The design answer is not to try to be exact there, but to wake early and say when instead of now: the thread wakes 30 ms before the target and hands the sound over together with the target instant.

3. The callback. A sound card does not take one sample at a time. The operating system's audio engine asks the program for a block of samples at regular intervals, by calling a function, the callback. In shared mode the interval is the engine's period and the block is one period long: on the Windows outputs measured so far 480 frames at 48 kHz, which is exactly 10.00 ms, so the callback runs 100 times a second. (The block is not the whole buffer: the engine keeps a larger endpoint buffer behind it, see stage 5.) The old design (rodio) put a new sound in a queue and the sound began in the next block: between 0 and 10 ms after the program asked, a different amount for each sound, depending on where in the block it happened to be asked. That is the jitter. A metronome click that was due 62.5 ms after the last one landed 60 ms or 70 ms after it, depending on the luck of the phase. The recording in the baseline showed exactly this: places in the bar that jumped between two positions 10.02 ms apart.

4. Render. The callback fills the buffer. What it puts in is the mix of every sound that is playing. The work is short, but it must be predictable: the buffer is due when it is due, whatever the program was doing.

5. The audio stack. In WASAPI shared mode the program does not talk to the sound card. It talks to the Windows audio engine, which mixes every program's sound and sends the sum to the driver. The engine works in periods (the 10 ms above) and writes the mix into an endpoint buffer that stays ahead of the hardware; measured here, that buffer is 22 ms deep, and a request for a smaller one is raised to 22 ms. The driver and the device add their own. This part is the same for every sound, so it is a constant, and almost certainly the largest. It cannot be influenced from a shared-mode program. The exclusive mode of WASAPI, ASIO and WDM-KS would remove most of it, and are out of scope by decision of the owner. The smaller-period call of shared mode, IAudioClient3, was studied and is a no-go on the outputs measured (see What cannot be improved).

6. Beyond the driver. The converter, a USB link, a Bluetooth radio, the cable. Bluetooth is the extreme: its codecs and buffers add 100-200 ms or more, which no program can hide. The manual says a Bluetooth output cannot be used for timing.

The input side has a delay of its own, which the clock cannot see either: from the stick hitting the pad through the module, the USB-MIDI link and the operating system to the moment midir's callback runs and the program reads Instant::now(). It is small and fairly steady, and calibration absorbs it as well: Calibrate measures the sum (output delay + input delay + the player's habit of anticipating the click), which is exactly what grading has to subtract.

The time model

The engine makes one decision about time, and everything else follows from it. A sound meant for time T is rendered at the frame of the stream that the sound card renders at T, and is heard one device latency later. It does not try to make the sound arrive at T. That is the same as it always was, and it is why calibration still works and why the playhead on screen runs a little ahead of what you hear (a known gap). The alternative, rendering at T minus the latency so that the sound is heard on the grid, needs a latency figure that can be trusted, and the one cpal gives is not that (see below).

The consequence is that the engine has to answer one question precisely: which frame of the stream is being rendered at the instant T of the program's clock? Everything in the engine is arranged around answering it without ever blocking the callback.

One sound, end to end

Take a snare hit in Listen, due at T = zero + t. The figure shows the stream's buffers as boxes, 10 ms each, with the callbacks at their edges.

  1. Cue to sink. run_with (playback.rs) walks the sorted cue list. For each cue it computes the target instant (zero + t, squeezed by the tempo ramp), waits until target minus the sink's lookahead(), and calls the pure function dispatch, which decides what sounds (the click switch, notes, the instrument's gain and mute, MIDI or audio) and calls the Sink with the target instant as when.
  2. Sink to engine. DeviceSink::audio_drum looks up the lane's sample (already at the stream's rate), its choke group, and calls EngineHandle::play. play asks Shared::frame_at(T) for the frame and pushes Command::Play(Trigger) into the queue. It does not wait for the sound.
  3. Callback. The backend's closure reads the clock first (origin.elapsed(), as early as it can, because its own lateness is what the estimate measures), then Callback::render feeds the estimator, publishes the new estimate, pops every command into the mixer, and renders.
  4. Mixer. A Trigger waits on a fixed-size list until the frame counter reaches its start_frame. Inside render the check is made frame by frame, so a sound whose frame lies in the middle of a block starts in the middle of the block: 288 frames in, in the example. That is the property the whole engine is for.
  5. Out. The mono mix is clamped to ±1, copied to every channel, converted to the device's sample format and handed back to cpal; the stream sends it on to Windows.

The clock: from an instant to a frame

The scheduler thinks in Instants; the mixer thinks in frames. Shared::frame_at converts: frame f is rendered at about intercept + f / rate seconds after the engine's origin, so T maps to (T - origin - intercept) * rate. The only unknown is the intercept, the moment the stream's frame 0 was rendered. The callback can observe it: it knows when it ran (wall) and which frame it started on, so wall - frame / rate is the intercept plus how late this callback ran.

That lateness is the enemy. Windows wakes the callback through several layers, and it can be a millisecond late or ten. If the engine used each callback's wall as it came, the scheduler's sounds would move by exactly the amount the callbacks do, and the jitter would be back. But a callback can be late and never early, so the best estimate of the intercept is the smallest value seen over the last 128 callbacks (about 1.3 s): the late ones fall away. A stall of a few callbacks is shrugged off; a sound card clock that runs a little fast or slow (tens of parts per million) is followed, because the window moves on.

What the callback may and may not do

The callback has about ten milliseconds to fill a buffer. A late buffer is not a slow response but an audible click, so the code that runs in it follows rules that the rest of the program does not:

  • No allocation. The voice pool (MAX_VOICES = 64) and the waiting list (MAX_PENDING = 256) are Vecs created at full capacity. A sound that does not fit is dropped and counted (dropped_voices, dropped_pending); it is never allocated for.
  • No locks. Commands arrive through a bounded, wait-free, single-producer queue (rtrb, QUEUE = 1024). The producer end is behind a Mutex so that several scheduler threads can take turns, but only they lock it; the callback only pops. A full queue is reported to the caller as PlayError::QueueFull.
  • No frees. A sample is an Arc<[f32]>. When a voice ends the callback must not drop the last reference, because freeing memory can take long enough to be heard; so it pushes the Arc into a second queue, the graveyard (GRAVEYARD = 256), and any later call to the handle empties it on the scheduler's side. A test checks the reference count before and after.
  • A raised priority, not set here. cpal puts its Windows render thread at THREAD_PRIORITY_TIME_CRITICAL itself (the repository has no unsafe code and sets no priority); a 3-minute soak with 90 s of full CPU load showed no late sound, so MMCSS was not needed.
  • No waiting for time. Everything the callback reads is an atomic or comes out of a queue. It publishes the clock estimate and the counters with relaxed stores; the ready flag uses release and acquire.
  • Late sounds are played, not skipped. A sound whose frame has already passed when the block starts begins at the block's first frame, and is counted (late, and worst_late in frames). A scheduler that wakes later than 250 ms after a target (MAX_LATE) drops the cue instead of playing a burst.

Runs, cancelling and choking

The stream outlives every run, and several runs can overlap (a Listen and an audition), so the engine needs to end one run's sounds without touching another's. Each Listen, take or audition takes a number from EngineHandle::new_run and every Trigger carries it. cancel_run drops the run's waiting sounds and fades out the playing ones over FADE_FRAMES = 256 frames (5.3 ms at 48 kHz) so there is no click. DeviceSink does this in its Drop, which is why stopping a Listen is just letting the sink go.

A closed hi-hat or the pedal cuts an open hi-hat that is still ringing. In a mixer that must not allocate, that is a bit mask, not a list of objects: a trigger has a group (the bit number a later sound can choke it by, or NO_GROUP) and a chokes mask (the groups it chokes when it starts). When a sound starts, the voices whose group is in its mask begin the same 256-frame fade. choke_groups(lane) in playback.rs derives both from Lane::can_be_choked and Lane::chokes.

MIDI beside the audio

MIDI has no buffer to place a sound in: a note is sent and the module plays it at once. So DeviceSink treats the two differently. Audio is handed over 30 ms early, with its instant. MIDI is held back (HeldNote, held) until its exact time, and flush sends what has come due; wait_for wakes up for the earliest held note on its way to the next cue. The sink reports next_due() so the wait loop knows. When the sink has no engine its look-ahead is zero and MIDI goes out at once, as it did before the engine existed.

The lifetime of the stream

  • Opened on first use, never at start-up. DrumApp::new does no device work (an invariant), so the output opens when the first sound starts: ensure_audio runs before every take, Listen, audition, calibration and metronome start. The first sound after a start therefore comes after a short pause while the device opens; a listening test found this acceptable, so no start-up step opens the device early.
  • Kept open. Opening a stream per start, as the old design did, cost time on the sound thread and dropped early clicks on a slow device. The engine stays open until something changes. The price is that the program shows in the Windows mixer and wakes every 10 ms while it is open.
  • Opened again by AudioOutput::ensure when the stream failed (an unplugged device sets failed from cpal's error callback; the render thread ends after one DeviceNotAvailable), when the device in the settings changed, or when the setting is System default and Windows' default output is no longer the open one. The last case needs its own check: a stream stays on the output it opened when only the default moves, and raises no error, so ensure compares the default's name with the open device at each start (must_reopen, a pure function with tests). It looks at each start, not while something plays, so a running Listen stays on the output it began on.
  • Errors reach the error bar through ErrorLog (show_sound_errors): the stream's own, the engine's "did not start in time", a missing device. A named output that is gone falls back to the default with a message.

Calibration and a stale latency

The stored latency_ms was measured with one engine: its callback period, its alignment, its device. A different engine or a different device changes it. The engine generation (ENGINE_GENERATION, 2 = this engine, 1 was rodio) is stored next to it in latency_engine, written by Calibrate and when the slider is moved. When they differ, Settings → Timing shows an amber note and a Keep this value button. There is deliberately no per-device map of latencies: one value, one warning.

Calibration is not a pure measurement of the output delay: it includes the input delay and how the player anticipates the click. For grading that is correct, because the same two things are present in every take.

Measuring it

Nothing in the test suite hears anything, and the real delay cannot be tested; the timing of the program's part can be measured from outside. tools/audio_baseline.ps1 starts the release build with its own settings folder, starts the metronome (240 BPM, sixteenths) by sending keys, records the default output by WASAPI loopback and runs examples/audio_probe.rs, which finds the sound starts, folds them over one bar, and reports the spread per place in the bar and the spacing of the clicks. What cannot be improved from here

  • The shared-mode period. Every output measured (eight, on two machines: Realtek, Bluetooth, a USB audio interface, AMD HD Audio and Steam's virtual devices) reports a shared-mode period range of exactly 480 frames, 10 ms, for IAudioClient3 as well. It has nothing smaller to offer, so a backend that asked for one would change nothing. The decision is no-go (task AUD-9); it would be worth revisiting only for a driver that offers a range. The experiment that could have changed that was run: Microsoft documents 128-480 frames for its inbox HD Audio driver, so a vendor codec driver might have been what hides the range. On the first machine the Realtek codec reported 480 frames on the vendor driver and on the inbox driver alike (task AUD-10, docs/audio-latency-study.md), so the decision stands.
  • The buffer cannot be made smaller by asking. A shared, event-driven stream gets an endpoint buffer of 22 ms (1056 frames) on every output measured; requests of 5 to 20 ms are raised to 22 ms and longer ones are honoured. That is why there is no buffer-size setting.
  • Exclusive mode, ASIO, WDM-KS are out of scope by the owner's decision.
  • Bluetooth. 100-200 ms and more; use a wired output or send the click to the V31.
  • The playhead runs ahead of the sound by the device's delay, and with audio and MIDI on at once the MIDI note comes out of the module before the computer's sound is heard. Rendering at T minus the latency would fix both, but needs a trustworthy latency figure (see the callout above).
  • Live switches lag by up to the look-ahead: the click switch, notes and the mixer act on sounds that are handed over after the change, so a sound already in the queue still plays.

Testing the engine without a sound card

Every part is pure, so the real-time claims are tested by simulating the callback:

  • mixer.rs: onset at the exact frame, mid-block start, choke fade, pool and waiting-list exhaustion with counters, cancel, and that rendering does not allocate.
  • clock.rs: the estimate on synthetic callbacks with random lateness and occasional long stalls, and with a sound card clock 100 ppm fast or slow.
  • handle.rs: NotReady before the first callback, a full queue, cancel reaching the mixer, the graveyard releasing the last reference, and the end-to-end test: sounds scheduled on the program's clock start within 0.5 ms of the frame the card's clock names, with callbacks up to 4 ms late, 9 ms stalls and ±80 ppm drift (it measures about 0.16 ms), where the old design jumped by 10 ms.
  • playback/tests.rs: dispatch and run_with against a fake Sink, including looping, the ramp, late cues and that the first cue of a looped pass is handed over ahead of its time.
  • app/audio_output.rs: must_reopen, as a pure function of five values.

Never open real audio in a unit test: set click_audio and playback_audio to false. What no test can check is that a real device makes the right sound at the right moment; for that, listen, run the loopback tool, and read the Sound page's counters afterwards.

When you change the engineRun cargo test, then tools/audio_baseline.ps1 before and after on the same machine (the numbers depend on the machine), then a soak with a load, and read Settings → Sound afterwards. A change that moves the click in time should raise ENGINE_GENERATION, so that users are told to calibrate again.

Glossary

Terms of this chapter, in alphabetical order. In the text above, the first use of each is underlined with dots and links here. Where a word has two senses in this chapter, both are given.

Allocation, free
Asking the system for memory while the program runs (growing a list, creating a box), and giving it back. How long either takes depends on what else the system is doing, so it can take longer than a callback has. The callback does neither; see What the callback may and may not do.
Arc
Rust's reference-counted pointer: several owners share one value, and it is freed when the last owner lets go. A drum sound is an Arc<[f32]>, so the scheduler, the queue and the mixer share one copy. The graveyard exists so that the last owner is never the callback.
Atomic
A number or flag that threads read and write without a lock, each access happening as one indivisible step. The clock estimate, the counters and the stop flags are atomics. A relaxed store is the cheapest kind; release and acquire additionally make everything written before the store visible to a thread that sees the flag.
Audio engine
Two things carry this name. The engine is this program's own code in src/audio/: the queue, the clock estimate, the mixer and the stream. The Windows audio engine is the system component that, in shared mode, mixes the sound of every program, applies effects and passes the sum to the driver; it wakes the program's callback once per period. The text says "Windows audio engine" or "operating system's audio engine" for the second.
Block
The frames one callback fills. In shared mode a block is one period long (480 frames, 10 ms on the outputs measured). The mixer accepts a block of any size, because other drivers and systems hand over other sizes. Some documents call it a buffer; this chapter keeps "buffer" for the endpoint buffer.
Callback
A function that the audio system calls, on a thread of its own, every time it needs the next block of samples. It has to finish before the hardware runs out of data; if it is late the output glitches (a click or a gap). cpal calls ours; Callback in handle.rs is what it does. Also audio callback.
Choke group
A bit number a sound can be cut off by. When a sound starts it can choke the groups in its mask: a closed hi-hat cuts an open one that is still ringing. Done with two integers per sound, so no list is needed in the callback.
Converter (DAC)
The digital-to-analogue converter that turns the stream of numbers into a voltage for the speaker. With a USB or Bluetooth output it is in the device, and the link to it has its own buffering.
cpal
The Rust library the engine uses to open an output stream on the system's audio interface (WASAPI on Windows, ALSA and others elsewhere). It creates the audio thread and calls the program's callback on it.
Cue
One thing to play at one moment of a run: a click or a drum hit, with its time in seconds from zero (Cue in playback.rs).
Drift, ppm
The sound card has its own clock crystal, which runs a little faster or slower than the computer's clock. The difference is small: parts per million (ppm); 100 ppm is 0.1 ms per second. The clock estimate has to follow it, or sounds placed far ahead would end up early or late.
Endpoint, endpoint buffer
Endpoint is Windows' word for an output device (speakers, headphones, a monitor's speakers). The endpoint buffer is the buffer between the Windows audio engine and the driver; it stays ahead of the hardware. For a shared, event-driven stream it was measured as 1056 frames, 22 ms, and a request for less is raised to that.
Exclusive mode, ASIO, WDM-KS
Ways to talk to the sound hardware without the Windows audio engine mixing in between: the program has the device to itself. They remove most of the delay and are out of scope by decision of the owner.
Fade-out
A short ramp to silence (256 frames, 5.3 ms at 48 kHz) used when a sound is choked or cancelled, because cutting a sound at a random sample makes an audible click.
Frame
One sample for each channel at one instant. At 48 kHz the stream plays 48,000 frames a second, so a frame lasts about 20.8 microseconds and 10 ms is 480 frames. The mixer counts frames from the first one it renders, and a sound is told to start at frame number N.
Graveyard
A second queue, from the callback to the scheduler side, into which the callback puts the sound data of finished sounds so that it never has to free memory itself.
Instant
Rust's type for a point on the computer's steady clock (std::time::Instant). Only the difference between two instants means something. The scheduler's clock; the engine's estimate converts it to a frame.
Intercept, origin
The origin is the instant the engine was opened. The intercept is the estimate of when, counting from the origin, the stream's frame 0 was rendered; frame f is then rendered at about intercept + f / rate.
Jitter
Variation of the delay from one sound to the next. A constant delay can be measured and subtracted; jitter cannot, because there is no single number.
Late sound
A sound handed to the engine after the frame it was meant to start at had already been rendered. It starts at the first frame of the block instead and is counted (the Sound page shows the count and the worst lateness).
Latency, delay
The time from the program deciding to play a sound to the sound being heard. This chapter uses delay and latency alike. A constant delay is the same for every sound; see jitter.
Lock, mutex
A Mutex lets one thread at a time use a value; a thread that finds it taken waits. Waiting is what the callback must never do, so the callback only touches things that need no lock.
Look-ahead
How far ahead of its time a sound is handed to the engine: 30 ms (AUDIO_LOOKAHEAD). It must exceed one block plus the lateness of the scheduler's wake-up, so that the command is in the queue before the callback that renders the sound's block runs.
Loopback recording
Recording what the program sends to an output, by tapping the Windows audio engine's mix (WASAPI loopback), instead of with a microphone. It sees the mix before the driver and the hardware, so it measures timing, not the full delay.
Mixer
The Mixer adds up all the sounds playing at a moment into one stream, starts waiting sounds at their frame, and applies fades and chokes. It is rendered from the audio callback, which is why it follows the callback's rules.
Voice
One sound that is playing, with its position in the sound data and its gain. The pool holds at most 64 voices; a sound that finds it full is dropped and counted.
MMCSS
The Multimedia Class Scheduler Service: a Windows service that gives threads registered as "Audio" or "Pro Audio" a protected priority. Not used here; cpal raises the render thread's priority itself.
Mono, channel
A channel is one stream of samples going to one speaker (left, right). The program's mix is mono, one channel, and the engine copies it to every channel of the device.
Onset
The moment a sound starts.
Period
The interval at which the Windows audio engine wakes the program's callback in shared mode (the shared-mode engine period): 10 ms on every output measured. One period is one block.
Thread priority
How readily the system gives a thread the processor. A thread at time-critical priority is run ahead of ordinary ones, which keeps the callback from being delayed by other work.
Queue, ring buffer
A fixed-size first-in first-out list between two threads. The engine's command queue is a ring buffer of 1024 entries with one writer end and one reader end (the crate rtrb).
Render
To compute the samples of a block. "Rendered at time T" means the frame the callback computes at that moment of the clock.
Resampling
Converting a sound to another sample rate. The drum kit is made at 44.1 kHz and the card usually runs at 48 kHz, so each sound is converted once per run with a windowed-sinc interpolator (it keeps the cymbals' high end and adds no false frequencies).
Run
One playing session of sounds that belong together: one Listen, one take, one audition. Each has a number, and cancelling ends exactly its sounds.
Sample
Two senses. (1) An audio sample is one number: the level of the signal at one instant. (2) A sample of the kit is a whole short sound, a snare or a click, stored as a list of such numbers (Arc<[f32]>). The context says which; "a block of samples" is the first, "the lane's sample" the second.
Sample rate, kHz
How many samples per channel the stream plays in a second; 48 kHz is 48,000. The sound card and Windows decide it; the program reads it and makes its sounds to match.
Scheduler
A thread (Player or Metronome) that walks the list of cues, waits for each one's moment and hands it on. It makes no sound itself.
Shared mode
The usual way of using WASAPI: the program's sound goes to the Windows audio engine, which mixes it with every other program's and sends the sum to the driver. Other programs keep working; the cost is the engine's period and buffer, which the program cannot change.
Sink
The trait that receives what a cue sounds like (an audio click, a MIDI drum). The real one drives the devices; tests pass a fake. See The Sink seam.
Spin
Waiting by running a tight loop and checking the clock instead of sleeping. It wastes processor time but ends exactly on time, so the scheduler sleeps in coarse steps and spins for the last 1.5 ms.
Spread
In the measurements: for one place in the bar, the difference between the earliest and the latest onset recorded there. A spread of 0.02 ms means the click never moved by more than that.
Stream
The open connection to one output device, through which the frames flow. The engine keeps one open; frames are numbered from the first it renders.
Estimator, clock estimate
The part of the callback that turns "when the callback ran" and "which frame it started on" into the intercept: the smallest recent value, so late callbacks do not count (Estimator in clock.rs).
Trigger, command
A Trigger is one sound to start: its frame, sound data, gain, run and choke groups. A command is what goes through the queue: Play(trigger) or CancelRun(run).
Wait-free
An operation that always finishes in a bounded number of steps whatever other threads do, because it never waits for one. Popping from the command queue is wait-free; that is why the callback may do it.
WASAPI
The Windows Audio Session API: how Windows programs play sound. It has a shared mode and an exclusive mode. cpal uses it on Windows.

7. The user interface

One frame

egui is immediate mode: there is no widget tree to keep in sync. Each frame the program runs update, which reads state, draws widgets and writes state back in the same calls. The order inside update matters:

  1. Start-up first: while startup is set, run_startup runs the next step and draws the splash; it answers with a Flow (see Start-up). Until the steps are done the main window is an empty panel and the frame ends here.
  2. Handle dropped files.
  3. update_state (before anything is drawn): sync_source puts the right practice source in place for the visible tab; drain_midi, update_controller and keyboard_pads turn input into state; sync_control, update_take, update_listen, update_metro, update_audition, update_calibration and show_sound_errors advance the state, steer the threads and surface errors.
  4. shortcut_keys: R, L, M, K, Esc, unless a text box is being typed in (widgets::typing; a button or slider with the focus does not count) or a key closed the splash in this frame.
  5. draw: the panels (sync_source again after the top bar, because a tab clicked now needs its source before it is drawn), then the windows that float above: the controller help screen and the Manage window (Windows).
  6. save_settings_if_changed: if cfg != saved_cfg, save the settings (so settings are persisted by diffing, not by event).
  7. schedule_repaint: continuously while recording, listening or calibrating; otherwise every 50 ms so the MIDI monitor stays live.

DrumApp is a single struct of about thirty fields, four of which are groups with an owner: view (ViewState: tab, Settings page, status line, error), midi (MidiState: ports, the drum input, the monitor, MIDI-learn), playback (Playback: Listen, its player and switches, the mixer's solo and audition) and metro_run (MetroState). Subsystems that grew large were moved to files under src/app/ as additional impl DrumApp blocks with pub(super) methods: the tabs (home.rs, score_tab.rs, results.rs, settings.rs, metro.rs, rudiment.rs), the take, Listen, audition and calibration lifecycles (session.rs), the mixer, the controller, the start trigger, the splash and the controller help screen. A child module sees its parent's private fields, so none of this needs accessors. The controller's own editor is one level deeper, src/app/controls/editor.rs, as a child module of controls.rs, so that it can read the private fields of Controller without making them public. That keeps one owner of the state while keeping files readable.

Visibility says who may call what: pub(super) inside app/ files means "the app module", pub(super) inside controls/editor.rs means "controls.rs only", and the one method app.rs must call from there, controller_editor_window, is pub(in crate::app).

Start-up

The first version of the program did all its device work in DrumApp::new: read the settings, list the MIDI ports and the sound outputs, open the drum module, open the controller. That is the wrong place for it. eframe creates the window hidden and shows it only after the first frame has been drawn, and it calls the app's constructor before that frame. Everything slow in new therefore delays the first visible window. Measured on the development machine (release build, no V31 and no controller attached), asking the sound system for its outputs took 260 to 400 ms of a start-up of 430 to 620 ms; opening a vendor's MIDI driver can take much longer and was not measured.

So new only sets up, and the slow work is a list of steps in app/startup.rs that run one per frame, with a splash window that names the step before it runs:

  1. Frame n: draw the splash with step k in progress and set drawn.
  2. Frame n+1: due() returns step k because the splash that names it is already on screen; run it (it may block), record a Line (what it found, and whether that is as hoped), draw the splash with step k+1 in progress.

The sound system is asked on a thread started in new (scan_sound_outputs), so the answer is usually ready when its step comes; if not, the step returns None and the frame repeats without blocking, and the spinner keeps turning. Steps that fail are not errors: the drum module not being there is the normal state of a development machine, and the line says so in amber.

The splash outlives the start-up. When the last step is done Startup records finished_at and the main window starts working (Flow::Go), but the splash stays until a key or a mouse button is pressed in either window. Two rules make that safe:

  • A grace period (GRACE, 0.6 s): input that arrives earlier is ignored, because clicks made while the program was busy arrive in a heap the moment it is free, and nobody has read the splash yet.
  • The closing key is not a shortcut. If a key closes the splash, run_startup answers Flow::KeyTaken and update skips the keyboard shortcuts for that frame, so pressing R does not also start a recording. A mouse click is passed on as usual.

8. The controller subsystem

A control surface is a set of controls that each send a MIDI message: a note, a controller number (cc) with a value, or a pitch-bend value. The subsystem turns those messages into actions of the program and the program's state into lights, and it can be taught a new device without writing code. It has an impure half that owns the MIDI port and a pure half that decides what everything means. The pure half is large (controller/, controller_layout.rs) and fully tested without a device.

Presets

A preset is a text file that says which message means which action. Supporting another surface is writing a text file, not code. The format is line based, # starts a comment, and a line that cannot be used becomes a warning while the rest still works:

name  = Behringer X-Touch Mini
port  = X-TOUCH MINI                  # part of the MIDI port's name
kind  = mackie                        # or midi
layer = A note 84                     # this message switches to layer A
bind  = A note 89 -> record           # a button, on layer A only
bind  = A cc 16 rel -> tempo          # an endless encoder (Mackie relative values)
bind  = cc 14 ch 2 rel twos -> tempo  # only on MIDI channel 2, two's complement
bind  = cc 13 abs -> tempo            # a knob that sends its position
bind  = bend 1 -> tempo               # a fader (pitch bend, channel 1)
led   = A record -> note 89           # a button light (on=127 off=0 unless the line says)
led   = record -> note 36 ch 10 on=21 off=0   # another channel and values (a pad's colour)
ring  = A tempo -> cc 48              # an LED ring (Mackie ring values)
ring  = tempo -> cc 20 scale=127      # a plain value 0..scale instead
{{code:core/src/controller/preset.rs::pub struct Binding}}
  • Kinds. A preset is mackie or midi (PresetKind). The kind decides how a ring is sent when the line has no scale=: Mackie's ring encoding (0x20 | position) for mackie, a plain 0 to 127 for midi. A file without a kind line is read as Mackie if it has layers or lights and as MIDI otherwise, which keeps files written before the line existed working: the kind only changes what a ring sends, and a preset without lights has none.
  • Layers. A line without a layer name applies to all layers; a line for the current layer wins over one for all layers. Lines that name an undeclared layer are dropped with a warning, and a control bound twice in the same place is reported (the first one is used).
  • Channels. ch N limits a binding to one MIDI channel. Preset::position looks a message up in four steps, most specific first: this layer and this channel, this layer, all layers and this channel, all layers. Called with no channel it means "any binding", which the pictures need because they cannot tell channels apart.
    • {{code:core/src/controller/preset.rs::pub fn position(}}
  • Where presets come from. BUILTIN holds the shipped ones; custom_presets(dir) lists the .txt files of the controllers folder next to the settings file, named after their file; preset_source(name, dir) says where the preset called name is (PresetSource::BuiltIn or File) and load_preset reads it. A built-in name always wins over a file of the same name, which is why the editor must never write to a file whose name is a built-in one.
  • Round trip. Preset::to_text writes a preset so that Preset::parse reads back the same value (comments are lost); a test checks it for every built-in preset. That property is what lets the editor use the file as its only storage.

The mapper

parse(bytes) -> Option<Msg>
Note on/off, control change and 14-bit pitch bend (the faders). Every Msg knows its MIDI channel.
Mapper::handle(msg, &State) -> Vec<Command>
Applies layer switching, Shift (held: encoder turns count five times, except browsing a list), relative-encoder decoding and fader pickup: an absolute control that does not move by itself must come within 3 % of the value it controls, or cross it, before it takes over, or the value would jump; it lets go again when the value drifts 25 % away.
Mapper::lights(&State) -> Vec<[u8; 3]>
The messages that bring lights and rings up to date: only what changed, the status byte carries the light's channel, and a light that is no longer wanted (another layer) is put out with its own off value.
Mapper::replace_preset(preset)
Puts an edited preset in place while the program runs. The layer and Shift stay; faders must catch up again and every light is sent again.

Editing presets: Learn

The Manage window edits presets without a text editor, and it is built on one decision: the preset file is the only storage. There is no copy of the preset in the editor's state. Every change does the same four things in edit_preset: read the chosen preset's file, apply the change to the Preset value, write the file, and give the result to the running mapper (replace_preset). The pure operations are in controller/:

{{code:core/src/controller/mapper.rs::pub fn learn(}} {{code:core/src/controller/preset.rs::pub fn assign(}}
  • learn(msg, action, relative, encoding, remember_channel) decides what a message says about the control that sent it, for the action that waits: a button needs a press (not the release), a value needs a cc or a fader, a list (Score, Rudiment) needs an endless encoder, a note is no use for a knob.   • Preset::assign binds the action to the control. The control is taken from whatever it was bound to on that layer (returned, so the window can say so), and the action's old control of the same kind (note, cc, fader) is replaced, while one of another kind stays: an encoder and a fader may both set the tempo.

The learn flow in editor.rs is a small state machine in EditorState (what the window itself remembers, such as the open flag, the rename text and the layer shown, is a separate ManageView in EditorState.view): learning holds the action that waits; learn_message consumes the next message, saves, and (if go on is ticked) sets learning to the next action in the list. Choosing a preset (select_preset) clears the flow. A click on a preset in the list chooses it as the one in use, not merely shows it: learning needs that preset's connection, and the editor can only edit what the mapper runs.

The folder of the user's presets comes from DrumApp.paths (Paths::controllers_dir): in the program the settings folder, in a test a temporary one. That is the seam that lets tests run a full learn, save, rename, copy and delete cycle without touching a real settings folder.

Testing the subsystem

  • The mapper is tested with plain messages and states: layers, Shift, pickup, every encoding, channels, light values, ring scales.
  • The built-in presets are parsed in a loop: no warnings, the right kind, a round trip through to_text, and a picture whose controls cover every binding.
  • Pictures are tested as geometry (see above), never by looking at pixels. Looking is done by hand, in the running program, once per layout change.
  • The editor is tested through its methods with a temporary folder: a learn cycle, steal and replace, channel and encoding choices, new, copy, rename and delete, refusal of bad names, and that a built-in preset is neither renamed nor deleted.
  • Nothing here has been tried on a real non-Mackie device: a mistake in a preset number is found with the monitor, and the preset is then fixed by learning the control again.

Design decisions worth knowing:

10. Settings and persistence

Settings are a small key = value text file (%APPDATA%\RollModel\config.txt and equivalents). There is no serialisation framework: each one-line setting is a row of the KEYS table (key, field, kind of value) that both Config::to_text and Config::from_text use, which keeps the file stable, hand-editable and tolerant. Lists and maps are written and read by hand.

{{code:core/src/config.rs::const KEYS::12}}

Where the file lives is a value, not a global: config::Paths (system(), in_dir(), none()) names the settings, sounds and controllers folders, Config::load_from(&paths) reads and save(&paths) writes, and DrumApp holds the one it uses.

  • Tolerant loading. Unknown keys are ignored, an unreadable value keeps the default, numbers are clamped, so a settings file from any earlier version loads.
  • Defaults are not written where that avoids clutter (mixer gains, per-rudiment tempos never changed).
  • Persistence by diffing: Config derives PartialEq, and update() saves when it differs from the last saved copy. UI code just mutates self.cfg.
  • Maps with prefixes (gain.Kick, rudiment_bpm.16) are parsed in the fallback arm of the match; BTreeMap keeps the written order deterministic.
  • Session-only state (practice tempo of a score, range, solo, lead override) is deliberately not in Config.
  • Controller presets are files too, but not in config.txt: the built-in ones are compiled in (BUILTIN), yours are .txt files in the controllers folder next to it. config.txt only remembers which one is chosen (controller_preset, controller_port); DEFAULT_CONTROLLER is the Mini, an empty value means "none" and is kept.
  • Every new key needs a round-trip test; roundtrip in config.rs compares whole Config values.
  • Config::migrate copies the settings folder of the old application name once; it is the pattern to follow for a future rename.

11. Rust constructs that carry the design

None of this is exotic Rust. The design leans on a handful of constructs used consistently. Each appears below with the real code.

Enums with data and exhaustive match

Closed sets of things are enums, and every match over them is exhaustive, so adding a variant produces compile errors at every place that must care. Lane, Action, Command, Msg, Grade, Tab, Source, Lead all work this way.

Traits as seams for testing

Sink separates "decide what to play" from "play it" (see the Sink seam). The trait is used as &mut dyn Sink: dynamic dispatch costs nothing that matters here, and the scheduler takes one reference instead of being generic.

Atomics behind Arc for live settings

Arc<Control> of AtomicBool/AtomicU32 with Relaxed ordering: independent flags and levels, no invariants spanning two of them, so nothing stronger is needed and no thread can block another.

RAII for threads

Thread handles wrap a stop flag and a JoinHandle; Drop stops and joins. Replacing an Option<Player> with None therefore stops its sound.

let … else for early exit

The code is full of let Some(x) = … else { return }. It keeps the happy path unindented and makes the preconditions of a function a list at its top, for example in ensure_rudiment:

Visibility as architecture

Guidelines

  • Put the test next to the code; prefer testing the pure function over testing through the UI.
  • A bug fix starts with a failing test.
  • Do not start real audio in a test: set cfg.click_audio and cfg.click_midi to false before start_take.
  • Tests that change shared tables (the catalogue size, the number of lanes) will fail loudly: update the counts in the tests deliberately.
  • A test that reads the user's real folders is fragile: it fails on a machine whose owner has made presets of their own. A DrumApp made for a test has Paths::none(); give it Paths::in_dir(temporary folder) when the test needs files, or compare only what the test controls.
  • To check an older commit (is every commit green?) export it with git archive and touch the files before building: files carry the commit's old timestamp and cargo then reuses a newer build.
  • Before committing: cargo test, cargo build (no warnings) and cargo check --no-default-features.

14. Tutorials

Each tutorial changes the real program and ends with tests. The code shown is what you type; names of existing items are real (look them up with the excerpts above). Create a branch first: git switch -c feature/<name> develop.

Tutorial 1: add a rudiment

small Goal: add a made-up rudiment Demo triple to the catalogue to see the mechanics. (Real rudiments are listed in docs/rudiments.md.)

  1. Write the pattern. Strokes are on a grid; > accents, a lower-case prefix is a flam. Three right strokes, an accented left, a flam: R R R L> lR on a 16th grid.
  2. Add the row to CATALOGUE and change the array length. The list is ordered by family, so the new number is the last of its family and everything after it shifts; for a quick experiment append it as number 41 and change [Rudiment; 40] to [Rudiment; 41]: 
        rud(41, "Demo triple", Family::Diddle, false, S16, "R R R L> lR", "An example rudiment for the tutorial."),
  3. Run the tests. They will tell you what encodes the old size: there_are_forty_numbered_in_order_with_the_known_counts (counts per family, 26 NARD), every_pattern_reads_and_has_the_length_of_the_catalogue (a beats table), the_sticking_is_the_one_of_the_chart if you add a row there. Update the counts and add the new rudiment's beats (5 strokes = 1.25 beats, rounded up to 2).
  4. Add a sticking test for the new row: 
    assert_eq!(rudiment(41).sticking(), "R R R L lR");
  5. Look at it. Run the program, open the Rudiments tab and pick it. Check that the flam's grace note is drawn left of its main note and that the default lead flows (the cell begins with R and ends with R, so the default is alternate).
  6. Docs. Add a row to docs/rudiments.md. The manual's reference table and this guide's counts regenerate themselves; the manual build checks that it finds exactly 40 rudiments, so change that number in tools/build_manual.py if you keep a 41st.
Next stepThe fixed-size array is the obstacle to user-added rudiments. Replace it with a Vec filled from the built-in table plus text files in a rudiments folder (copy controller::custom_presets), and parse with parse(), reporting bad lines as warnings like Preset::parse does.

Tutorial 2: add a setting

small Goal: a Show hand letters checkbox that hides the sticking letters.

  1. Config. In core/src/config.rs add the field, its default and one row of KEYS; the row is both the reader and the writer: 
    // struct Config
pub show_sticking: bool,
// Default
show_sticking: true,
// KEYS
key!("show_sticking", c.show_sticking, Flag),
    The kind says how the text is read: Text, Flag, number(lo, hi) (kept in range, a bad value changes nothing), LaneName or RudimentNumber. A list or a map needs code in to_text and from_text instead.
  2. Test. Add the field to the roundtrip test (set it to false so it differs from the default) and run cargo test config. A forgotten writer or reader fails there.
  3. UI. A setting goes on the page it belongs to. In settings_general (app/settings.rs) add: 
    ui.checkbox(&mut self.cfg.show_sticking, "Show hand letters under the notes");
    Saving is automatic: update() notices cfg != saved_cfg.
  4. Use it. The renderer must not read Config, so pass the flag through the view struct: add pub show_hands: bool to ScoreView, set it where the view is built in score_body (show_hands: self.cfg.show_sticking), and guard the draw_hand call in render::show with view.show_hands. The metronome's RollingView can stay as it is.
  5. Docs. One line in the changelog under [Unreleased], one in the manual's Settings page and its settings-key table.

Tutorial 3: add a metric to the report

small Goal: report the longest streak of perfect notes.

  1. Field. In analysis.rs add pub best_streak: usize to Report (it derives Default, so nothing else needs initialising).
  2. Compute. In summarize the loop over r.expected.iter().zip(&r.results) already visits notes in time order. Add a running counter next to the other accumulators: 
    let (mut streak, mut best) = (0usize, 0usize);
// inside the loop, after the pending / optional-grace checks:
if res.grade == Grade::Perfect {
    streak += 1;
    best = best.max(streak);
} else if !e.grace {
    streak = 0;
}
// after the loop:
r.best_streak = best;
  3. Test in analysis.rs, in the style of perfect_take_scores_high: twenty exact hits, one hit 70 ms late, twenty more; assert best_streak == 20.
  4. Show it. In results_tab add a row to the metrics grid: row("Longest streak of perfect notes", r.best_streak.to_string());.
  5. Optional feedback. In feedback() push a sentence when the streak is short compared with r.evaluated. Keep feedback sentences actionable.

Tutorial 4: add a controller action

small Goal: a button that toggles follow (the score scrolling with the playhead).

  1. Name it. In controller/action.rs add Follow to enum Action (under the buttons) and one row to ACTIONS: the word for preset files ("follow"), the label and the sentence the controller help screen shows, Class::Button, and light: true if the button should light. Names, texts, the editor list and has_light all read that row; the test every_action_has_a_name_a_title_and_an_explanation fails if the row is missing. A light also needs a follow: bool in State and an arm in State::lit.
  2. Do it. In app/controls/apply.rs, press(): 
    Action::Follow => self.follow = !self.follow,
    and, if you added a light, fill follow: self.follow in controller_state().
  3. Bind it. In a preset, for example a copy of the Mini preset in your controllers folder: bind = A note 94 -> follow (replace the "discard take" button) and led = A follow -> note 94.
  4. Test in controls/tests.rs like switches_and_tabs: 
    let mut app = app_with_score();
assert!(app.follow);
app.apply_command(Command::Press(Action::Follow));
assert!(!app.follow);
    and a Mapper test in controller/ that a preset line binding follow parses without warnings and a note-on yields Command::Press(Action::Follow).
  5. Docs. The button list in the README and the manual's controller section.

A value action (an encoder or fader) additionally goes into is_level, State::level and turn()/set(); look at Repeats as the model.

Tutorial 5: add a tab

medium Goal: a Stats tab that lists the session's takes.

  1. Enum and bar. In app.rs add Stats to enum Tab, a selectable_value line in top_bar and an arm in the match self.tab that fills the central panel: Tab::Stats => self.stats_tab(ui),. The compiler points at the other match on Tab you must extend.
  2. Module. Create src/app/stats.rs and declare it with mod stats; next to mod mixer;: 
    //! The Stats tab: every take of this session in one table.

use super::DrumApp;

impl DrumApp {
    pub(super) fn stats_tab(&mut self, ui: &mut egui::Ui) {
        ui.heading("Session");
        egui::Grid::new("stats").striped(true).show(ui, |ui| {
            for t in self.history.iter().rev() {
                ui.label(t.number.to_string());
                ui.label(t.range.as_str());
                ui.label(format!("{:.0} {}", t.overall, t.letter));
                ui.end_row();
            }
        });
    }
}
  3. Which session? The history is per practice source (it is swapped with the source). Decide whether the new tab shows the active one (as here) or reads self.parked.history too. Tabs other than Score and Rudiments leave the source as it is.
  4. Keyboard tab cycling. Add Tab::Stats to the list in next_tab (app/controls/apply.rs) and fix the expected order in switches_and_tabs.
  5. Test that it draws: copy the_tab_draws_for_every_rudiment (a headless Context::run calling app.stats_tab(ui)) and add a take to the history first.
  6. Docs. A section in the manual, a line in the changelog, the module list in HANDOFF.md.

Tutorial 6: add an instrument

medium Goal: a Rim click lane, separate from the cross-stick.

  1. Enum. Add RimClick to enum Lane and to Lane::ALL (change the array length from 18 to 19). Everything sized from Lane::ALL.len(), such as the atomic array in Control, follows.
  2. Let the compiler lead. cargo build lists each exhaustive match on Lane that lacks the new variant: name (settings key), label (shown name), standard_note (General MIDI key, for example 37 is taken by the cross-stick; pick a free note), default_staff (position and notehead) and the synthesiser in synth.rs. Give it a sound: copy a similar lane's recipe and change its parameters.
  3. Family. If it is easily confused with another instrument and should earn partial credit, put it in the same family() arm (here: with CrossStick and Snare).
  4. Mapper and groups. Add the MIDI notes to NoteMap::roland_v31() if the module has the pad. For the controller's mixer strips add it to a group in controller::group_lanes (a test requires every instrument but Other to be in exactly one group).
  5. Import. Teach gm_lane, lane_from_name and lane_from_staff if scores should map to it.
  6. Tests that now fail show what else to adapt (the kit test renders every lane, the config test writes map. and gain. for every lane). Add a test that the new lane's default MIDI note maps back to it.
  7. Settings files need no migration: map.<Name> keys are read by Lane::from_name, unknown names are ignored, and a lane without a stored map gets the defaults.

Tutorial 7: test sound without a sound card

small Goal: a test that the click is silenced during the music but not during the count-in. The pattern applies to anything that decides what sounds.

  1. Find the helpers. The tests module of playback.rs defines a Fake sink that records Ev events, opts() (a PlayOptions with audio and MIDI on), click(t) and drum(lane, t) to make cues, and play(cue, opts, control) which runs dispatch once and returns the recorded events. PlayOptions has no Default, so build on opts().
  2. Read the existing test. This exact behaviour is already covered; it is the model to copy. The live switch is in Control, the count-in is a cue at negative time: {{code:src/playback/tests.rs::fn click_switch_mutes_the_music_but_not_the_count_in}}
  3. Write yours the same way: build the Control and cues, call play(&cue, &opts(), &control), assert on the returned events. Run it with cargo test click_switch. Change one thing (for example a second Control with set_notes(false)) to see the test fail for the right reason.
  4. Time-dependent behaviour (looping, stopping, late cues) goes through run_with, which takes the zero instant, the cues, a stop flag and the sink, with a short tail, so a test can run a real pass in a few milliseconds. Look at looping_repeats_until_switched_off_and_finishes_the_pass.
What cannot be testedThat a real device makes the right sound at the right moment. Check it by ear and, on Windows, with the per-application peak meter, and record the result in HANDOFF.md. The timing of the engine can be measured from outside, by loopback recording (Measuring it).

Tutorial 8: support another controller

Goal: a preset for a pad controller, then (optionally) a drawn picture.

  1. Find the numbers. Select the controller in Settings → Controller, press every control and read the monitor: it shows note 36, cc 13 = 77 or bend 1 and the channel.
  2. Write the file. presets/my-pads.txt with name, port (part of the MIDI port's name), kind = midi and one bind per control. Tutorial 9: add a step to the start-up

Goal: something slow that the program does at launch, shown on the splash.

  1. Name it. Add a variant to enum Step in app/startup.rs and put it in the list in Startup::new at the place where its inputs exist (after Settings if it needs the configuration).
  2. Say what it is doing. An arm in label(): "Reading the thing…" (while it runs the user sees this text).
  3. Do the work. An arm in run_step that returns a Line: what it found, and ok: false if that is not as hoped (it shows in amber). If the work can be long and does not need the UI thread, start it on a thread in new as the sound scan does and return None until the answer is there.

15. Releases and CI

.github/workflows/release.yml builds on pushes to main, on tags vX.Y.Z and on the preview tag (only when its commit is on develop).

  1. plan decides whether to build at all (a branch push of a commit that also carries a release tag is covered by the tag run).
  2. manual (Ubuntu) runs the three Python tools: the user manual, the developer guide and the third-party notices, and uploads them as one artifact.
  3. build-linux and build-windows (both on GitHub-hosted runners; Windows uses the GNU toolchain, x86_64-pc-windows-gnu, so the program needs no Visual C++ runtime) runcargo test --release, cargo build --release and package the binary with README.md, CHANGELOG.md, LICENSE, the manual, the developer guide, the notices and examples/.
  4. publish attaches everything to a GitHub release (a normal one for v*.*.*, a replaced pre-release for preview).

.github/workflows/ci.yml runs cargo test --release on every push to develop, on hosted Ubuntu and Windows with the same toolchains. It has no pull_request trigger on purpose: the repository takes no outside pull requests, and no workflow may use a self-hosted runner.

.github/workflows/pages.yml publishes the documentation on every push to main (which only receives releases, so the site shows the latest release): tools/build_site.py builds a start page and runs the same two scripts as the release into manual/ and developer/, and the three official Pages actions upload and deploy the folder. The release files do not depend on it. The repository's Pages source must be set to GitHub Actions.

Making a release

  2. Merge to main, tag vX.Y.Z and push the tag. The workflow does the rest.
  3. A pre-release from develop: git tag -f preview && git push -f origin preview.

16. Known gaps and roadmap

  • V31 and controllers are untested on hardware. The note map is the common Roland V-Drums factory map; the hi-hat pedal polarity (127 = closed) is the Roland convention; the Mackie presets are from the Mackie Control table and the four generic presets are from memory (a web search confirmed only a few of their numbers). Learning against a real device has not been tried.
  • The preset editor binds actions, creates and deletes layers and gives actions lights and rings (all with the same defaults: the control the action is bound to), and editing rewrites the file without its comments. The generated help picture does not show where the controls are on the device.
  • Large files and structs. (Mostly done; see CD-14, CD-13 and CD-5 in HANDOFF.md for what is left.) app.rs holds DrumApp, whose fields are grouped (ViewState, MidiState, Playback, MetroState, the rest still flat), and the MIDI, keyboard and file handling; the tabs and the take, Listen and calibration lifecycles are in app/home.rs, score_tab.rs, results.rs, settings.rs and session.rs. HANDOFF.md lists the review of them against clean-design rules.
  • Nobody has listened to the synthesised kit (only spectral guards test it). The built-in sounds are intentionally simple.
  • Notation: proportional spacing; beams, flags, tuplet brackets and rests are worked out from the onsets (no note lengths in the score), so ties are not drawn, a rest the file does not print is not drawn, and the Metronome tab's staff has no beams.
  • MusicXML: D.S./D.C./coda are not followed, score-timewise is rejected, only the first drum-looking part is used.
  • Audio delay. The engine removes the jitter, not the constant delay of the operating system's shared mode (one 10 ms period at least on every output measured). The latency figure of the Sound page is a lower bound, the playhead runs ahead of the sound by the device delay, and a Bluetooth output is unusable for timing. See What cannot be improved; HANDOFF.md has the open study.
  • Two timing threads with duplicated click logic (task CD-5, to be done with a real take on a release build).
  • No persistence of takes; CSV export only.
  • Follow mode scrolls every frame while recording, so manual scrolling is impossible during a take.
  • The weights of the overall score are first guesses and need tuning with real takes.
  • Bar numbers: bars show their printed number, the sliders use the position; with repeats expanded the two differ.

The living list is in HANDOFF.md under "Todo" and "Known gaps".

17. Invariants checklist

Before you commit, check you did not break one of these.

  • Score positions are quarter notes; seconds only through TempoMap.
  • Take time zero is the start of the first measure of the range; start_take adds 0.5 s lead plus the count-in.
  • Hit timestamps come from Instant::now() in the MIDI callback; latency_ms is subtracted when a hit is recorded.
  • Staff step 0 is the bottom line (E4), 8 the top (F5).
  • Matching is greedy, one-to-one, cheapest first; grace notes are optional; later notes stay pending.
  • The pure modules do not import GUI, MIDI or audio code.
  • Callbacks only push to queues; sound threads never block on the UI; the UI thread owns DrumApp.
  • The audio callback never allocates, locks or frees: fixed pools, a wait-free queue in, a graveyard queue out, atomics for everything it publishes. A sound is told to the engine with the instant it should start, about 30 ms ahead; MIDI is held back to its time.
  • A change that moves the click in time raises audio::ENGINE_GENERATION, so that a stored latency is flagged as stale. The output opens at the first sound, never in DrumApp::new.
  • Every slider goes through widgets::slider; new settings go on their page and into config.rs with a round-trip test.
  • Practice fields are swapped only by activate; open_file activates the Score source.
  • Rudiment scores are written at BASE_BPM, so the practice tempo in percent is the BPM.
  • Listen and takes share plan_run; changing it changes both.
  • Shortcuts are ignored while a text box is being typed in, and in the frame in which a key closed the splash.
  • DrumApp::new does no device or file work; it becomes a step in app/startup.rs.
  • A controller preset file is the only storage of its assignments: the editor reads it, changes it, writes it and puts the result in the mapper. to_text and parse round-trip.
  • A built-in preset is never written to; an editable preset is one whose name is not a built-in name and whose file is in the user's folder.
  • A layout holds numbers only; every binding of a built-in preset is on a control of its picture; every action has a title and an explanation.
  • Windows: the splash and the Manage window are immediate viewports with an embedded fallback; the help screen is an egui::Window.
  • New glyphs are checked in the running app; new user-visible behaviour is in the changelog, the manual and HANDOFF.md.
